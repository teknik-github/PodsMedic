Kubernetes SRE agent · Go · self-hosted

Your cluster tells you it is broken.
PodsMedic tells you why.

It watches for failing pods, gathers the evidence a human would — describe, events, logs, node capacity — and asks an LLM what went wrong. Then, if you let it, it applies the fix, checks whether the fix held, and rolls it back if it did not.

Apache 2.0 · self-hosted · stdlib + client-go + one model SDK · no agent sidecars, no SaaS, nothing leaves your cluster but the evidence you configure.

The container is killed with exit code 137 roughly every four minutes because its 128Mi memory limit is below the ~210Mi the JVM heap settles at under load. Raise the limit to 256Mi.

healed memory limit 128Mi → 256Mi on Deployment/web · verified after 10m · no recurrence

Plain language, not a stack trace. The change, if it made one, is named — and so is whether it held.

One loop, once per interval

Nothing here is event-driven except the display. Healing is deliberately paced, because a repair loop that reacts instantly is a repair loop that can thrash a cluster instantly.

  1. 1

    Detect

    OOM kills, crash loops, image-pull failures, unschedulable pods, restart storms, stuck volumes, unbound claims. Plus prediction: memory trending into an OOM is flagged before the kill.

  2. 2

    Correlate

    Symptoms are grouped into one incident, so a pod failing five ways is one alert and one diagnosis — not five.

  3. 3

    Collect

    Events, logs, container spec, probes, volume claims, node conditions, and the cluster's real headroom. Environment variable names only — never values.

  4. 4

    Diagnose

    The model returns a schema-constrained answer: what broke, why, and a proposed action. Or the playbook answers it for free — see below.

  5. 5

    Validate

    A pure function re-derives a bounded plan from live cluster state, or refuses. This is the part that matters, and it has its own section.

  6. 6

    Verify

    A later sweep re-checks the workload. If it did not recover, the change is rolled back and the remedy is forgotten.

The part worth reading

Pod logs reach the model. So the model is untrusted.

Anything an attacker can write to a log, they can say to the LLM. That makes every answer it returns — including its proposed fix — untrusted input, and no amount of prompt wording changes it.

So the model's proposal is never applied. It is handed to heal.Validate, a pure function with no cluster access, which re-derives a bounded plan from the current state of your cluster or refuses outright. It is exhaustively unit-tested, and every rule below is a test that fails loudly if someone loosens it.

Replica counts are never taken from the model either. They are computed from measured load with the same formula an HPA uses; the model may only lower the result, never raise it.

  • Values only ever increase. The worst case of a wrong answer is a workload with too much.
  • Absolute and relative caps. Nothing grows past your ceiling, or past a multiple of what it had.
  • Image tags only. Repository and registry are pinned; the model cannot repoint an image.
  • Probes loosen, never tighten.
  • Capacity is physics, not policy. Headroom is bin-packed per node — a pod fits on one node, so cluster-wide sums lie. Pod slots count. A reserve is held back.
  • No capacity reading, no scaling. It refuses rather than guessing a default.
  • An HPA forbids scaling outright. Two controllers writing replicas overwrite each other.
  • Namespace allow/deny, kind allowlist, confidence floor.

Two switches, and the middle one is real

PODSMEDIC_AUTOHEAL=falseDiagnose and alert. Nothing is proposed.
AUTOHEAL=true · HEAL_APPLY=falseFull validation and a genuine server-side dry run. The API server checks the change; nothing persists.
HEAL_APPLY=trueChanges are applied, verified, and rolled back on failure.

Both default to off. You opt in twice, on purpose.

What it fixes, and what it refuses to

The second column is not a roadmap. Each one is a decision where acting automatically would be more dangerous than the fault.

Handles automatically

  • OOM kills — raises the memory limit within your caps
  • Memory or CPU trending into failure — raises it before the kill
  • Load needing more replicas — derived from measurement, gated on real headroom
  • Probes too aggressive for a slow starter — loosens them
  • A missing PersistentVolumeClaim — creates it from your configured defaults
  • Storage recovered but the pod stuck on a stale mount — restarts it
  • A problem it has fixed before — replays the remedy with no LLM call at all

Diagnoses, then stops

  • Application bugs. No resource change fixes wrong logic.
  • Wrong or missing config and secrets. It does not know the right value, and guessing one is worse than failing.
  • A mistyped image. Letting a model repoint an image is a supply-chain hole opened via a log line.
  • Sick nodes. It has no write permission on nodes and must not gain one — draining is a decision far larger than patching a workload.
  • Oversized requests. Lowering a request moves the scheduling floor and eviction priority. That call stays with you.
  • Mass failure. When many workloads fail at once the cause is usually one thing; healing suspends itself rather than patching thirty controllers blind.

What else is in the box

It learns, and it forgets

A fix that is applied and later verified goes into a playbook, and the next occurrence is repaired with no model call — no cost, no latency, same safety checks. A remedy that stops holding is dropped at once, repeat offenders are quarantined, and anything unconfirmed for too long retires so the model re-diagnoses it fresh.

Brakes at two scopes

Per workload: a cooldown and a circuit breaker that suspends healing after repeated rollbacks. Cluster-wide: a per-sweep budget and a surge guard counted over distinct workloads, so one Deployment with thirty crashing replicas stays one failure.

Node health, one stage earlier

Every other signal starts from a pod, so it arrives after the pods have already fallen over. A node reports DiskPressure or NotReady first. Report-only, always.

Rightsizing you apply yourself

Measures real usage against declared requests and suggests corrections — from the observed peak times a headroom factor, never the mean, because a container that idles at 10m and spikes to 900m needs the 900m.

A daily digest, even on quiet days

Every other message is failure-triggered, which leaves "nothing is broken" and "the agent died" looking identical. This one arrives either way, so its absence is itself the signal.

An audit trail and a study document

Every change, dry run, verification and rollback is recorded. Export the whole thing as Markdown or a printable HTML document describing how this cluster actually fails.

Built in, off by default

A live view where motion is the signal

Each namespace is an orbital shell; every workload rides it. A workload with an open problem stops dead while its shell-mates keep going past it. Colour needs you to be looking at it. A motionless dot in a field of moving ones does not.

It updates in seconds from a pod watch, while everything the agent does stays on its interval. One embedded page, no CDN, no fonts, no libraries — a globe of dots is projection arithmetic, which does not justify a dependency.

  • Token-gated. It refuses to start on a network-reachable address without one.
  • Honours reduced-motion — and says so, instead of looking broken.
  • No Service, no Ingress. kubectl port-forward is the intended route.

Ask it questions. It will not take orders.

The Telegram channel is two-way, allowlisted, and rate limited. It is also structurally read-only: there is no path from a message to the healer, and the question-answering model is given no action to propose.

  • /statusWhat the last sweep found
  • /incidentsWhat is open right now
  • /capacityHeadroom exactly as the validator sees it
  • /nodesHealth of the machines underneath
  • /healsRecent changes, and whether they held
  • /playbookRemedies it can replay without the model
  • /rightsizeRequests that do not match reality

Try it in about a minute

A dry run touches nothing: it reads your current kubectl context and prints what it would say to stdout.

1Run it locally, changing nothing

export ANTHROPIC_API_KEY=sk-ant-...
make run

2Point it at a chat

export SLACK_WEBHOOK_URL=https://hooks.slack.com/services/...
go run ./cmd/podsmedic

3Deploy it to the cluster

kubectl apply -f deploy/config.yaml
kubectl apply -f deploy/rbac.yaml
kubectl -n podsmedic create secret generic podsmedic \
  --from-literal=ANTHROPIC_API_KEY=sk-ant-... \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -f deploy/deployment.yaml

Settings and workload are separate files on purpose, so rolling out a new image cannot silently reset every setting you tuned.

It starts read-only. Healing is two deliberate switches away, and everything it would have done is printed first.
